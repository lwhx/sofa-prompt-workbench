# 沙发场景提示词工作台全量优化计划

> 计划日期：2026-08-08  
> 编制日期：2026-08-09  
> 状态：已实施（阶段 0～5 完成，阶段 6 待 Docker/Playwright 环境验证）  
> 依据：当前代码、`sofa_prompt_workbench_development_spec_v1_reliable_cn.md`、`CLAUDE.md` 与本地质量门禁实测

## 1. 目标与边界

本计划在不改变 V1 核心业务语义的前提下，逐步补齐可靠性闭环，降低前后端耦合和数据库读写放大，恢复严格质量门禁，并建立可观测、可迁移、可灰度、可回滚的交付路径。

### 1.1 优化目标

1. 保持任务快照不可变、`row_revision`/`input_fingerprint` CAS、结果防陈旧覆盖、SQLite Outbox 和确定性 RQ Job ID 等现有不变量。
2. 补齐自动运行 Intent、维护调度、Redis/RQ 对账、备份保留和垃圾回收的生产闭环。
3. 将 SSE 从“每个连接每秒扫描并哈希全量业务表”调整为“提交后发布失效事件，断线时轮询兜底”。
4. 缩短 SQLite 写事务，隔离 AI 网络调用与数据库会话，提升失败恢复和取消行为的一致性。
5. 收敛前端重复拉取、超大页面组件、重复错误提示和首屏大包问题。
6. 使后端 Ruff、Mypy、Pytest，前端 Lint、类型检查、单测、构建，E2E 与容器检查成为一致且可复现的 CI 门禁。
7. 加固登录限流、代理来源识别、外部地址校验、健康检查、密钥轮换和审计能力。

### 1.2 非目标

- 本轮不迁移到 PostgreSQL，不引入 Kubernetes，不拆分微服务。
- 本轮不替换 Vue 3、FastAPI、SQLAlchemy、SQLite、Redis/RQ、OneImg 或 OpenAI 兼容协议。
- 本轮不改变提示词业务规则、六模块结果结构及人工方位确认语义。
- 未完成基准和容量验证前，不通过增加 Uvicorn 多进程规避 SQLite 并发问题。

- 已有数据库备份、完整性检查、外键检查、隔离恢复校验及相应单元测试。

## 3. 架构决策

### ADR-01：保留模块化单体与 SQLite，设置迁移触发线

**决策**：继续使用单 FastAPI 写入入口、独立 RQ Worker/Dispatcher/Maintenance 和文件型 SQLite WAL，不立即迁移 PostgreSQL。

**理由**：当前是单管理员工具，主要耗时在外部 AI 推理；现有 CAS、Outbox、WAL 和单写入拓扑可满足近期规模，直接换库会扩大验证和回滚面。

**约束**：所有外部网络调用必须位于 SQLite 写事务外；API 暂保持单 Uvicorn Worker；定期记录锁等待、数据库大小、WAL 大小和写事务耗时。

**迁移触发线**：连续 7 天任一条件成立时启动 PostgreSQL ADR：写锁等待 P95 大于 100 ms、`database is locked` 超过 0.1%、活跃任务行超过 10 万、需要多 API 写实例或备份窗口无法满足 RPO。

### ADR-02：采用“事务 Outbox + Redis 通知 + 数据库真相源”

**决策**：SQLite 继续作为任务意图和状态真相源；Redis 仅承载 RQ、短期限流和失效通知，不承载不可恢复业务状态。

**方案对比**：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| SSE 每连接轮询数据库 | 实现简单，不依赖 Redis Pub/Sub | 连接数乘以全表扫描，扩展性差 | 仅保留为临时兼容路径 |
| 提交后直接 Redis Pub/Sub | 延迟低、实现较轻 | 提交与发布存在丢消息窗口 | 配合版本水位和前端补拉采用 |
| 新增事件 Outbox 再投递 | 可审计、可补发、可靠性最高 | 增加表、清理和调度复杂度 | 若通知丢失指标超标再升级 |

**落地**：第一阶段采用提交后 Pub/Sub，并在 SSE 重连、页面重新可见和定时兜底时读取数据库；事件只携带 `scope`、`row_ids`、`event_version`，不携带完整结果。若实测仍出现不可接受的通知缺口，再新增事件 Outbox。

### ADR-03：Worker 使用短事务状态机

**决策**：将任务执行拆为 Claim、Prepare、External Call、Finalize 四段。每段创建短生命周期 Session；外部 AI 调用期间不保留 ORM Session 和写事务；Finalize 继续使用 CAS。

**失败语义**：

- Claim 失败：幂等返回，不重复执行。
- 外部调用失败：记录 Attempt，按错误分类决定重试或终止。
- Finalize 前取消：进入 `CANCELED`，不写当前结果指针。
- Finalize CAS 不匹配：结果可作为 stale 历史保留，但不得更新 `latest_result_id`、`selected_result_id` 或当前行状态。
- Worker 进程丢失：心跳超时后由维护任务与 RQ Registry 对账，再决定重投或失败。

### ADR-04：Vue Query 管理服务端状态，Pinia 管理本地交互状态

**决策**：按垂直切片引入 `@tanstack/vue-query`，先迁移 rows，再迁移 assets、results 和 admin；Pinia 保留选区、通知偏好、对话框和本地 Mutation 队列。

**理由**：项目规范已指定 Vue Query；其查询去重、失效、重试、请求取消和陈旧数据策略能替代当前重复的全量刷新逻辑。

**兼容策略**：迁移期间保留现有 Store 外观，内部逐步委托 QueryClient，避免一次性重写页面。

### ADR-05：安全校验集中化并默认拒绝

**决策**：OneImg 和 AI 服务共用外联策略模块，集中处理协议、主机、端口、DNS 解析、私网/回环/链路本地地址、凭据 URL、重定向逐跳验证和超时。

**默认策略**：生产环境只允许 HTTPS；私网目标默认拒绝，必须通过显式 allowlist 开启；响应和日志不记录 Token、Cookie、完整图片 Base64 与未脱敏供应商响应。

## 4. 分阶段实施计划

### 阶段 0：基线冻结与门禁修复（P0，1～2 个工作日）

**目标**：先建立可信基线，任何后续优化都能被重复验证。

**实施项**：

1. 使用锁文件重新同步后端开发依赖，修复损坏的本地 Pytest 环境。
2. 修复 9 个 Mypy 错误，不通过扩大全局 `ignore_missing_imports` 或滥用 `Any` 绕过。
3. CI 后端任务增加 `uv run mypy app`，命令与 `CLAUDE.md` 保持一致。
4. CI 增加 Alembic upgrade、空库 schema 校验和迁移 head 唯一性检查。
5. CI 增加依赖锁文件一致性、前端构建产物阈值报告；Compose 检查放入具备 Docker 的独立 Job。
6. 记录当前 API、SSE、任务调度和前端构建基线，测试输出不包含真实凭据。

**验收**：本地与 CI 的 Ruff、Mypy、Pytest、ESLint、Vue 类型检查、Vitest、Build 全绿；CI 不再跳过 Mypy；迁移测试从空数据库可升级到 head。

**回滚**：仅回滚 CI 和类型修复提交；不得回滚锁文件到无法安装状态。若新门禁暴露历史问题，可临时将门禁设为非阻塞最多 2 个工作日，并创建明确到期项，不允许删除检查。

### 阶段 1：任务可靠性与维护闭环（P0，3～5 个工作日）

**目标**：让 Intent、Outbox、RQ、心跳恢复和维护任务形成一致状态机。

**实施项**：

1. 实现 `AutoRunIntent` upsert、到期 claim、revision 校验、输入冻结和 Job + Outbox 同事务创建。
2. 为 Intent 增加 claim token/租约或等价 CAS 字段，防止 Dispatcher 与 Maintenance 重复消费。
3. 统一 Dispatcher 职责：只负责 Outbox 投递和快速对账；Maintenance 负责 Intent、僵尸任务、备份、WAL checkpoint、Outbox 保留和垃圾回收。
4. 对 `PENDING_DISPATCH`、`QUEUED`、`RUNNING` 与 RQ queued/started/failed/finished registry 建立对账矩阵。
5. Worker 移除 `Base.metadata.create_all`，启动前只检查 Alembic revision，不隐式修改生产结构。
6. 将 Worker 重构为短事务状态机，Attempt 编号改为并发安全的唯一约束重试或数据库 CAS。
7. 统一可重试错误分类，限制最大尝试次数并加入指数退避和抖动；鉴权、非法图片、用户取消、永久校验失败不自动重试。
8. 增加 Redis 清空、Worker 强杀、Dispatcher 重启、重复 enqueue、Finalize CAS 冲突的集成测试。

**验收**：同一行任意时刻最多一个活动 Job；Intent 重复消费不产生重复 Job；Redis 清空后可由数据库意图恢复；外部 AI 调用期间无 SQLite 写事务；旧 Job 永不覆盖新 revision；故障注入后任务在约定时间内收敛到可重试或终态。

**回滚**：新维护逻辑通过配置开关启用；回滚时先停止新 Maintenance 调度，再等待已 claim 租约过期，恢复旧 Dispatcher；保留新增字段和表，不执行破坏性 downgrade；所有 `DISPATCHING` 项回置为可重试状态后再切换。

### 阶段 2：实时事件与查询性能（P0/P1，3～4 个工作日）

**目标**：消除 SSE 按连接全表轮询，降低列表和结果查询放大。

**实施项**：

1. 增加统一领域事件发布器，在数据库提交成功后发布失效通知；发布失败只计指标，不回滚业务事务。
2. SSE 服务订阅 Redis 频道，发送 `row_ids` 与单调递增 `event_version`；保留 keepalive。
3. 前端在断线、重连、窗口重新可见时立即刷新；SSE 不可用时以 5～10 秒带抖动轮询，不与正常 SSE 重复轮询。
4. `/rows` 查询增加分页/游标、可选 `updated_after` 或行 ID 过滤；为常用过滤和排序补充复合索引。
5. 消除列表中的潜在 N+1 和全量结果计数扫描，使用聚合子查询或维护字段，并以 `EXPLAIN QUERY PLAN` 验证索引命中。
6. 建立 SSE 连接数、事件发布失败数、前端轮询降级数、列表查询耗时与扫描行数指标。

**验收**：稳定 SSE 连接期间不再每秒扫描 Job/Result 全表；事件延迟 P95 小于 2 秒；模拟丢消息或 Redis 短暂中断后，前端最多在一个兜底周期内恢复正确状态；1 万任务行基准下列表 P95 满足 300 ms 目标。

**回滚**：保留 `SSE_MODE=polling|pubsub` 双模式一个发布周期；回滚到 polling 时限制连接数并提高轮询间隔；前端始终保留轮询兜底，因此后端切换不要求同步回滚前端。

### 阶段 3：安全、配置与可观测性（P0/P1，3～5 个工作日）

**目标**：封闭外联、认证和运维盲区。

**实施项**：

1. 新增统一外联 URL 策略，覆盖 AI 配置测试、正式推理与 OneImg；禁止 URL 凭据、非预期端口、危险 IP 和未经校验重定向。
2. 登录限流迁移到 Redis 原子滑动窗口；仅在配置的可信代理链下读取转发 IP；增加用户名 + IP 双维度限制。
3. 密钥加密派生加入 key version，支持旧密钥解密、新密钥写入和批量轮换；轮换过程不在日志输出明文。
4. 扩展就绪检查：Alembic revision、SQLite 读写条件、Redis/RQ、数据目录、必要生产配置；外部 AI 和 OneImg 采用独立深度检查，不阻塞基础就绪。
5. 为请求、Job、Attempt 增加关联 ID 和结构化日志；补充队列深度、Outbox 年龄、Intent 年龄、Job 各阶段耗时、Token 用量、失败分类、数据库/WAL 大小和最近备份时间指标。
6. 统一审计目录，覆盖登录失败、上传、绑定、删除、运行、取消、重试、结果选择、人工确认、设置、备份与恢复。
7. 对敏感日志、错误响应和管理端脱敏结果增加自动化测试。

**验收**：SSRF 测试覆盖回环、私网、IPv6、本地域名、DNS 变化和重定向；多实例下登录限流一致；旧配置可在轮换期读取且新写入使用新 key version；健康检查能区分存活、基础就绪和外部依赖异常；日志扫描不出现密钥、Cookie 和图片 Base64。

**回滚**：URL allowlist 和 Redis 限流支持配置切换；安全策略只能回滚到“更严格或等价”，不得为了兼容开放任意内网；密钥轮换在确认所有密文重加密和备份验证前不得删除旧密钥。

### 阶段 4：前端状态治理与组件拆分（P1，4～6 个工作日）

**目标**：降低请求竞争、页面复杂度和首屏成本，不改变用户操作路径。

**实施项**：

1. 引入 Vue Query，先将 rows 查询和 Mutation 迁移为查询缓存、精确失效与乐观更新；再迁移 assets、results、admin。
2. 为列表刷新增加请求单飞、取消和响应序列保护，禁止旧响应覆盖新状态。
3. Mutation 优先使用后端返回的最新行局部更新；仅在冲突、SSE 失效或批量操作后执行精确重拉。
4. 拆分 `WorkbenchView.vue`：工具栏、网格配置、运行控制、实时同步、图片预览和结果对话框编排。
5. 拆分 `AdminView.vue`：模板管理、AI 能力配置、审计列表三个独立面板和查询模块。
6. 将 API 响应 envelope、错误码、Row/Job/Result 状态改为共享类型和判别联合，减少字符串集合漂移。
7. 统一错误展示责任：HTTP 层处理会话失效，业务层处理可操作错误，避免拦截器与页面重复弹窗。
8. 路由继续懒加载，Element Plus 使用按需组件/样式，AG Grid 只在工作台路由加载；设置构建包体预算。
9. 增加窗口恢复、SSE/轮询切换、并发 Mutation、409 冲突、请求乱序和批量操作测试。

**验收**：同一 rows 查询并发只发一个请求；旧响应不能覆盖新状态；稳定 SSE 下无固定 3 秒重复轮询；页面功能和可访问性回归通过；vendor 初始加载体积较基线显著下降，且每个关键 chunk 不突破批准预算。

**回滚**：以资源域为单位切换 Vue Query，不一次删除旧 Store；保留兼容适配层一个发布周期；组件拆分保持 props/emits 契约，出现回归可逐面板回滚，不回滚后端 API。

### 阶段 5：备份、迁移与发布工程（P1/P2，3～5 个工作日）

**目标**：使结构变更、数据恢复和生产发布可演练、可证明。

**实施项**：

1. 增加定时数据库备份、保留策略、失败告警和恢复演练；Manifest 记录应用版本、Alembic revision、哈希、表计数和对象清单状态。
2. 建立 OneImg 对象库存导出与引用核对；明确“仅数据库恢复”和“完整业务恢复”的不同 RPO/RTO。
3. 数据库迁移统一采用 Expand → Backfill → Dual Read/Write → Contract；大批量回填分批提交并可续跑。
4. 每个迁移发布前自动创建已验证备份，发布后执行 `integrity_check`、`foreign_key_check`、revision 和核心计数核对。
5. 增加真实 Compose E2E：迁移、登录、上传替身、创建任务、入队、Worker 替身完成、SSE 更新、结果查看、备份恢复。
6. 发布采用单机蓝绿应用镜像 + 共享数据前的停写窗口；数据库结构必须至少兼容前后两个应用版本。
7. 制定运行手册：Redis 丢失、Worker 卡死、SQLite 锁、AI 超时、OneImg 故障、备份失败和密钥轮换。

**验收**：备份自动生成并通过隔离恢复；恢复演练满足数据库 RPO 24 小时、RTO 60 分钟的初始目标，最终目标由业务确认；前一版本应用可在 Expand 阶段继续运行；Compose E2E 覆盖核心真实链路。

**回滚**：应用镜像可回退一版；数据库优先前滚修复，禁止自动执行破坏性 downgrade；若迁移导致数据错误，停止写入、保存故障现场、从发布前已验证备份恢复到新文件，再原子替换数据库并重新对账 Redis/RQ。

### 阶段 6：容量验证与持续优化（P2，持续）

**目标**：以指标决定是否继续优化或迁移基础设施。

**实施项**：

1. 建立 1 千、1 万、10 万任务行的列表、SSE、结果历史和维护扫描基准。
2. 对 1、5、10 个并发 AI Job 验证队列等待、SQLite 锁、心跳和取消延迟。
3. 为 AI 模型建立黄金样例回归：结构有效率、方向判断一致率、人工复核率、提示词长度、失败率、Token 与单任务成本。
4. 建立供应商超时、429、5xx、截断输出和非法 JSON 的故障注入测试。
5. 按 ADR-01 触发线决定是否启动 PostgreSQL、多 API 实例或独立事件存储方案。

**验收**：形成可重复的容量报告和趋势面板；任何扩容或换库决策都有数据依据；模型变更必须通过黄金样例和成本阈值。

**回滚**：性能优化必须保持行为测试不变；缓存、批量和并发参数配置化，可快速恢复保守值；模型升级使用版本固定和小流量验证，异常时回到上一模型/模板版本。

## 5. 数据库迁移策略

### 5.1 迁移原则

1. 所有结构变更由 Alembic 管理，应用运行时不得 `create_all`。
2. 每个 revision 必须包含 upgrade 验证；生产数据相关迁移必须提供前向修复说明，不依赖破坏性 downgrade。
3. 先加可空字段、索引或新表，再回填和双写，最后在至少一个稳定发布周期后收紧约束。
4. SQLite 需要重建表时使用 batch mode；迁移前后执行完整性、外键、索引和核心计数检查。
5. 回填必须幂等、分批、可观察、可续跑，避免单次长写事务阻塞 API 与心跳。

### 5.2 预期结构变更

| 迁移 | 目的 | 建议结构 | 兼容方式 |
|---|---|---|---|
| M-01 | Intent 并发 claim | `claim_token`、`lease_expires_at`、`attempt_count`、`last_error`，以及 `(status, due_at)` 索引 | 旧记录默认可重新 claim |
| M-02 | 事件版本水位 | 轻量 `event_sequence` 或应用设置中的单调版本 | 旧 SSE 客户端忽略新增字段 |
| M-03 | 查询性能 | Job 活跃状态/心跳、Result 行版本、Outbox 状态/下次尝试、Row 删除/更新时间复合索引 | 仅新增索引，无 API 破坏 |
| M-04 | 密钥轮换 | `AppSetting.key_version` 或加密 envelope 内版本 | 先双读旧/新格式，只写新格式 |
| M-05 | 审计与可观测 | 审计关联 ID、Actor、结果、脱敏详情版本 | 新字段可空，后台渐进展示 |
| M-06 | 可选事件 Outbox | `domain_event_outbox`，含 aggregate、version、payload、状态和保留时间 | 仅在 Pub/Sub 缺口指标触发后实施 |

### 5.3 发布迁移顺序

1. 停止自动发布，确认队列和数据库健康。
2. 创建并验证发布前备份，记录 Manifest 与当前 revision。
3. 部署兼容新旧结构的应用版本，但暂不开启新功能开关。
4. 执行 Expand migration 和分批 backfill。
5. 执行校验查询、完整性检查和影子读取对比。
6. 小范围开启新读路径，再开启新写路径。
7. 观察至少一个稳定周期后停止旧写入。
8. 后续独立发布执行 Contract，删除旧字段或兼容代码。

## 6. 验收体系

### 6.1 功能与不变量验收

- 同一行活动 Job 唯一，重复点击和重复投递均幂等。
- 输入修改后旧任务结果只能成为 stale 历史，不能更新当前指针。
- 自动运行仅消费到期且 revision 匹配的 Intent。
- Redis、SSE 或浏览器短暂断线不造成永久错误状态。
- 取消、失败、超时和 Worker 崩溃后 `active_job_id` 最终释放。
- 数据库提交成功而通知失败时，前端通过重连或轮询恢复。
- 备份恢复后核心表计数、外键、结果版本和对象清单一致。

### 6.2 质量门禁验收

```text
后端：Ruff → Mypy strict → Pytest → Alembic upgrade/schema check
前端：ESLint → vue-tsc → Vitest → production build → bundle budget
系统：Compose config/build → integration E2E → backup/restore drill
安全：SSRF → auth/rate-limit → secret/log scan → dependency audit
AI：schema regression → golden cases → cost/latency threshold
```

任何 P0/P1 阶段进入下一阶段前，其新增行为必须具备单元测试和至少一个跨模块集成测试；可靠性修复必须包含对应故障注入测试。

### 6.3 初始 SLO 与性能阈值

| 指标 | 初始目标 |
|---|---|
| 普通 API 可用性 | 月度不低于 99.5% |
| 列表查询 P95 | 1 万行数据集下小于 300 ms |
| Mutation API P95 | 不含上传和外部 AI，小于 500 ms |
| SSE 失效通知 P95 | 小于 2 秒 |
| 任务状态最终收敛 | Worker/Redis 短故障恢复后小于 5 分钟 |
| 陈旧结果覆盖 | 0 次 |
| Outbox 最老待投递年龄 | 正常状态小于 30 秒 |
| 数据库锁错误率 | 小于 0.1% |
| 数据库备份 | 每日至少 1 次且验证成功 |
| 日志敏感信息泄露 | 0 次 |

AI 推理时延受供应商影响，应按模型分别记录 P50/P95/P99，不与普通 API SLO 混合。

## 7. 总体回滚方案

### 7.1 回滚分级

- **L1 配置回滚**：关闭 Pub/Sub SSE、Vue Query 新路径、自动运行消费或新重试策略，恢复保守参数。
- **L2 应用回滚**：切回上一镜像；要求数据库处于 Expand 兼容期，且上一版本能忽略新增表和可空字段。
- **L3 数据修复**：停止相关消费者，保留数据库现场，运行幂等修复脚本并重新对账 Outbox/RQ。
- **L4 数据恢复**：全局停写，从发布前已验证备份恢复到新文件，执行完整校验后原子切换，再重建 Redis 短期状态。

### 7.2 回滚触发条件

满足任一条件立即停止扩量并评估回滚：陈旧结果覆盖、重复活动 Job、不可逆数据丢失、登录绕过或 SSRF、错误率较基线翻倍、SQLite 锁错误超过 1%、核心 E2E 失败、备份完整性检查失败。

### 7.3 回滚操作顺序

1. 冻结新发布和功能开关，记录时间点、版本、revision 与指标。
2. 停止产生新写入的入口或消费者，不直接删除 Redis/SQLite 数据。
3. 判断采用 L1、L2、L3 或 L4，优先配置回滚和前滚修复。
4. 若涉及队列，先停止 Worker/Dispatcher/Maintenance，再处理数据库状态和 RQ Registry。
5. 恢复后执行完整性、外键、核心计数、活动 Job 唯一性和 stale CAS 检查。
6. 逐步恢复 Dispatcher、Maintenance、Worker、API 写入和前端流量。
7. 完成事故复盘和测试补充后才能重新开启优化路径。

## 8. 实施顺序与依赖

```text
阶段 0 基线门禁
  └─→ 阶段 1 任务可靠性
       ├─→ 阶段 2 实时事件与查询
       └─→ 阶段 3 安全与可观测性
             └─→ 阶段 4 前端状态治理
                   └─→ 阶段 5 备份迁移与发布
                         └─→ 阶段 6 容量验证
```

- 阶段 0、1 为上线前阻断项，不应与大规模前端重构并行。
- 阶段 2 的后端事件契约稳定后，阶段 4 才迁移前端失效策略。
- 阶段 3 的指标和关联 ID 应先于阶段 5 的灰度发布启用。
- 每个阶段独立提交、独立迁移、独立功能开关、独立验收，不混入无关重构。

## 9. 完成定义

本计划完成需同时满足：P0/P1 优化项关闭；所有质量门禁持续通过；自动运行、Outbox、RQ 与恢复闭环通过故障注入；SSE 不再按连接扫描全量业务表；外联安全策略和分布式登录限流生效；前端无请求乱序覆盖；备份恢复完成演练；发布和回滚手册可由非开发值班人员按步骤执行；容量与 AI 黄金样例报告已归档。
